# CryptoCore

**CryptoCore** — учебный проект по реализации, исследованию и тестированию криптографических алгоритмов на Python с интерфейсом командной строки (CLI).

Разработка выполнялась последовательно в рамках восьми спринтов. Каждый новый спринт расширял функциональность проекта с сохранением возможностей предыдущих этапов.

**Текущая версия: `0.8.2` — дополнительное исправление замечаний безопасности после Sprint 8.**

**Последняя проверка (Windows, Python 3.14.0): 422 успешно пройденных теста, 95,22% покрытия строк и ветвей, 87/87 публичных определений документированы.**

## 1. Возможности проекта

| Спринт | Реализованная функциональность |
|---|---|
| Sprint 1 | AES-128 в режиме ECB, PKCS#7, работа с файлами, CLI |
| Sprint 2 | AES-CBC, CFB, OFB, CTR, автоматическая генерация IV |
| Sprint 3 | CSPRNG на основе `os.urandom()`, генерация ключей, статистические проверки и NIST STS |
| Sprint 4 | Собственные SHA-256 и SHA3-256, потоковое хеширование и benchmark |
| Sprint 5 | Собственный HMAC-SHA256, контроль целостности, RFC 2104 и RFC 4231 |
| Sprint 6 | AES-GCM, GHASH, Encrypt-then-MAC, AAD, аутентифицированное шифрование |
| Sprint 7 | PBKDF2-HMAC-SHA256, иерархия ключей, команда `derive`, salt, итерации и очистка секретных буферов |
| Sprint 8 | Документация API, руководство пользователя, автоматизация тестов, audit и документация безопасности |

Реализованные криптографические функции проверяются автоматическими тестами, известными тестовыми векторами и сравнением с независимыми реализациями.

Проект предназначен для образовательных целей и не является криптографической библиотекой, прошедшей независимый аудит безопасности.

## 3. Sprint 1 — AES-128 в режиме ECB

В первом спринте реализована поддержка алгоритма AES-128 в режиме ECB.

Для AES-128 используется ключ размером 16 байт, представленный в CLI как строка из 32 шестнадцатеричных символов.

Для данных, длина которых не кратна размеру блока AES, применяется дополнение PKCS#7.

### 3.1. Шифрование

```powershell
cryptocore --algorithm aes --mode ecb --encrypt --key 000102030405060708090a0b0c0d0e0f --input plaintext.txt --output ciphertext.bin
```

### 3.2. Расшифрование

```powershell
cryptocore --algorithm aes --mode ecb --decrypt --key 000102030405060708090a0b0c0d0e0f --input ciphertext.bin --output decrypted.txt
```

### 3.3. Проверка корректности

В рамках первого спринта реализованы тесты:

- обработки файлов;
- корректности AES-128;
- добавления и удаления PKCS#7;
- проверки ключей;
- полного цикла шифрования и расшифрования;
- обработки ошибок.

**Ограничение безопасности:** режим ECB раскрывает структуру повторяющихся блоков исходных данных и не рекомендуется для шифрования реальной конфиденциальной информации.

## 4. Sprint 2 — режимы работы AES

Во втором спринте добавлены режимы CBC, CFB, OFB и CTR.

| Режим | Дополнение | IV |
|---|---|---|
| ECB | PKCS#7 | Не требуется |
| CBC | PKCS#7 | 16 байт |
| CFB | Не требуется | 16 байт |
| OFB | Не требуется | 16 байт |
| CTR | Не требуется | 16 байт |

Для CBC, CFB, OFB и CTR при обычном шифровании автоматически создаётся случайный IV.

Формат сохранения результата:

```text
IV (16 байт) || Ciphertext
```

При расшифровании IV считывается из начала файла.

### 4.1. Пример CBC

Шифрование:

```powershell
cryptocore --algorithm aes --mode cbc --encrypt --key 000102030405060708090a0b0c0d0e0f --input plaintext.txt --output cbc.bin
```

Расшифрование:

```powershell
cryptocore --algorithm aes --mode cbc --decrypt --key 000102030405060708090a0b0c0d0e0f --input cbc.bin --output decrypted.txt
```

### 4.2. Пример CTR

```powershell
cryptocore --algorithm aes --mode ctr --encrypt --key 000102030405060708090a0b0c0d0e0f --input plaintext.txt --output ctr.bin
```

```powershell
cryptocore --algorithm aes --mode ctr --decrypt --key 000102030405060708090a0b0c0d0e0f --input ctr.bin --output decrypted.txt
```

Режимы ECB, CBC, CFB, OFB и CTR сами по себе не обеспечивают криптографическую проверку подлинности данных. Для защиты от незаметной модификации в Sprint 6 добавлены GCM и Encrypt-then-MAC.

## 5. Sprint 3 — криптографически стойкий генератор случайных данных

Реализация находится в:

```text
src/cryptocore/csprng.py
```

Основная функция:

```python
generate_random_bytes(num_bytes)
```

Для генерации случайных значений применяется `os.urandom()`, использующий криптографически стойкий источник случайных байтов операционной системы.

Обычный генератор `random` не используется для создания криптографических ключей или IV.

### 5.1. Автоматическая генерация AES-ключа

Если при шифровании не указан `--key`, CryptoCore может сгенерировать случайный 16-байтный ключ AES-128.

Пример:

```powershell
cryptocore --algorithm aes --mode ctr --encrypt --input plaintext.txt --output ciphertext.bin
```

Программа **не выводит секретный ключ в stdout по умолчанию**. Для автоматической генерации она создаёт отдельный файл `<output>.key` с 16 бинарными байтами. Используйте `--key-file` для расшифрования; `--show-key` специально включает опасный вывод HEX-ключа.

Для последующего расшифрования необходимо сохранить этот ключ.

### 5.2. Тестирование генератора

Проводились проверки:

- генерации случайных ключей;
- отсутствия повторений в тестовых наборах;
- распределения нулей и единиц;
- статистических характеристик последовательностей;
- испытаний с использованием NIST Statistical Test Suite.

Статистические тесты позволяют оценивать отдельные свойства последовательностей, но сами по себе не доказывают криптографическую стойкость генератора.

## 6. Sprint 4 — SHA-256 и SHA3-256

Исходные файлы:

```text
src/hash/sha256.py
src/hash/sha3_256.py
```

SHA-256 и SHA3-256 реализованы самостоятельно без использования `hashlib` для вычисления хеша внутри соответствующих алгоритмов.

`hashlib` используется в тестах для независимого сравнения результатов.

### 6.1. SHA-256

Реализация соответствует конструкции SHA-256, описанной в FIPS 180-4.

Алгоритм обрабатывает блоки размером 512 бит и использует 64 раунда преобразования.

Результат — 256-битное значение.

### 6.2. SHA3-256

Алгоритм SHA3-256 основан на губчатой конструкции Keccak-f[1600].

Используется 24 раунда преобразования состояния.

Результат — 256-битное значение.

### 6.3. Вычисление хеша через CLI

SHA-256:

```powershell
cryptocore dgst --algorithm sha256 --input document.pdf
```

SHA3-256:

```powershell
cryptocore dgst --algorithm sha3-256 --input document.pdf
```

Сохранение результата:

```powershell
cryptocore dgst --algorithm sha256 --input document.pdf --output document.sha256
```

Формат строки результата:

```text
HASH_VALUE  INPUT_FILE_PATH
```

### 6.4. Потоковое хеширование

Хешируемые файлы читаются блоками по 8192 байт.

Это позволяет обрабатывать большие файлы без необходимости целиком загружать их содержимое в оперативную память.

### 6.5. Проверка известных векторов

Хеш SHA-256 пустой строки:

```text
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
```

Хеш SHA3-256 пустой строки:

```text
a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a
```

В тестах проверяются известные ответы, обработка пустого ввода, обновление состояния частями, лавинный эффект и совпадение с эталонными реализациями.

### 6.6. Производительность

## 7. Sprint 5 — HMAC-SHA256

Реализация:

```text
src/mac/hmac.py
```

HMAC-SHA256 реализован на основе собственного SHA-256 из Sprint 4.

Конструкция соответствует RFC 2104.

Формула:

```text
HMAC(K, m) = SHA256((K' XOR opad) || SHA256((K' XOR ipad) || m))
```

Здесь `K'` — ключ после нормализации до размера блока SHA-256, `ipad` и `opad` — установленные константы.

HMAC используется для проверки целостности и подлинности сообщения при наличии общего секретного ключа.

HMAC не шифрует сообщение.

### 7.1. Вычисление HMAC

```powershell
cryptocore dgst --algorithm sha256 --hmac --key 00112233445566778899aabbccddeeff --input message.txt
```

Ключ для HMAC передаётся в HEX и может иметь переменную длину.

### 7.2. Сохранение HMAC

```powershell
cryptocore dgst --algorithm sha256 --hmac --key 00112233445566778899aabbccddeeff --input message.txt --output message.hmac
```

### 7.3. Проверка HMAC

```powershell
cryptocore dgst --algorithm sha256 --hmac --key 00112233445566778899aabbccddeeff --input message.txt --verify message.hmac
```

При совпадении:

```text
[OK] HMAC verification successful
```

При ошибке:

```text
[ERROR] HMAC verification failed
```

Для сравнения используется `secrets.compare_digest()`.

### 7.4. Тестирование

Реализация проверена на тестовых векторах RFC 4231.

В частности, для пароля-ключа из 20 байтов `0b` и сообщения `Hi There` ожидаемое значение:

```text
b0344c61d8db38535ca8afceaf0bf12b881dc200c9833da726e9376c2e32cff7
```

Проверяются ключи разной длины, изменение содержимого сообщения, неверный ключ, пустой файл и потоковая обработка.

Для проверки больших файлов предусмотрен:

```text
scripts/test_large_hmac.py
```

## 8. Sprint 6 — аутентифицированное шифрование

В шестом спринте реализованы два механизма:

- AES-GCM;
- Encrypt-then-MAC.

Они позволяют не только зашифровать информацию, но и обнаруживать изменение защищённых данных.

### 8.1. AES-GCM

Реализация:

```text
src/modes/gcm.py
```

GCM сочетает шифрование на основе AES-CTR и аутентификацию через GHASH.

В модуле самостоятельно реализованы:

- формирование счётчиков;
- операция `inc32`;
- GHASH;
- умножение в `GF(2^128)`;
- вычисление аутентификационного тега;
- проверка тега до передачи открытого текста вызывающему коду.

Для базового преобразования AES используется PyCryptodome.

Стандартный формат файла GCM:

```text
Nonce (12 байт) || Ciphertext || Tag (16 байт)
```

При обычном шифровании nonce генерируется случайно.

Повторное использование одного и того же nonce с одним ключом GCM недопустимо. Файловый CLI версии 0.8.1 регистрирует пары ключ+nonce/IV в локальной SQLite-базе и отклоняет повтор; это не гарантирует уникальности между независимыми компьютерами.

### 8.2. Шифрование с AAD

AAD (*Additional Authenticated Data*) — дополнительные аутентифицируемые данные.

AAD не шифруются, но участвуют в вычислении тега аутентификации.

Шифрование:

```powershell
cryptocore --algorithm aes --mode gcm --encrypt --key 00112233445566778899aabbccddeeff --input plaintext.txt --output ciphertext.bin --aad aabbccddeeff
```

Расшифрование:

```powershell
cryptocore --algorithm aes --mode gcm --decrypt --key 00112233445566778899aabbccddeeff --input ciphertext.bin --output decrypted.txt --aad aabbccddeeff
```

При успешной проверке:

```text
[SUCCESS] Decryption completed successfully
```

При неверном AAD, изменённом шифртексте или неправильном теге происходит отказ в аутентификации.

Открытый текст не записывается в выходной файл до успешной проверки.

### 8.3. AAD из файла

Для GCM и EtM предусмотрен параметр `--aad-file`, позволяющий передавать дополнительные аутентифицируемые данные из бинарного файла.

```powershell
cryptocore --algorithm aes --mode gcm --encrypt --key 00112233445566778899aabbccddeeff --input plaintext.txt --output ciphertext.bin --aad-file metadata.bin
```

```powershell
cryptocore --algorithm aes --mode gcm --decrypt --key 00112233445566778899aabbccddeeff --input ciphertext.bin --output decrypted.txt --aad-file metadata.bin
```

AAD читается блоками, что уменьшает потребление оперативной памяти.

Одновременно передавать `--aad` и `--aad-file` нельзя.

Проверен сценарий потокового чтения AAD объёмом 16 МиБ.

Сценарий:

```powershell
python scripts\test_large_aad.py --size-mb 16
```

Отдельная проверка AAD, превышающего физически доступную оперативную память, не проводилась.

В версии 0.8.1 основной файловый CLI работает потоково (блоки до 64 КиБ) для всех режимов. В библиотечных функциях, принимающих `bytes`, весь вход по-прежнему передаётся в памяти.

### 8.4. Encrypt-then-MAC

Реализация:

```text
src/aead/encrypt_then_mac.py
```

EtM объединяет AES-CTR и HMAC-SHA256.

Из общего master key с различными контекстными метками получаются отдельные ключи шифрования и аутентификации.

Формат файла:

```text
Nonce (16 байт) || Ciphertext || HMAC (32 байта)
```

Шифрование:

```powershell
cryptocore --algorithm aes --mode etm --encrypt --key 00112233445566778899aabbccddeeff --input plaintext.txt --output ciphertext.bin --aad aabbccddeeff
```

Расшифрование:

```powershell
cryptocore --algorithm aes --mode etm --decrypt --key 00112233445566778899aabbccddeeff --input ciphertext.bin --output decrypted.txt --aad aabbccddeeff
```

Проверка HMAC выполняется до AES-расшифрования.

### 8.5. Тестирование AEAD

Проверены:

- известные тестовые векторы NIST для GCM;
- совместимость вычислений GCM с PyCryptodome;
- полный цикл шифрования и расшифрования;
- неверный AAD;
- изменение nonce, шифртекста и тега;
- отсутствие записи открытого текста при провале аутентификации;
- сохранение существующего файла при ошибке проверки;
- 1000 уникальных nonce;
- пустой AAD;
- потоковое чтение AAD;
- независимое вычисление HMAC для EtM.

В тесте `test_etm_independent_mac_reference` сравнивается полный производный ключевой материал для шифрования с полным ключом аутентификации. Сравнение только усечённого ключа шифрования с 32-байтным ключом аутентификации не используется в качестве доказательства разделения ключей.

## 9. Sprint 7 — PBKDF2 и иерархия ключей

Седьмой спринт посвящён функциям получения криптографических ключей из паролей и разделению ключевого материала по назначению.

Реализованы:

```text
src/kdf/pbkdf2.py
src/kdf/hkdf.py
```

Алгоритмы используют собственный HMAC-SHA256 из Sprint 5.

### 9.1. PBKDF2-HMAC-SHA256

PBKDF2 (*Password-Based Key Derivation Function 2*) — функция получения ключевого материала из пароля.

Результат зависит от четырёх параметров:

- пароля `password`;
- соли `salt`;
- количества итераций `iterations`;
- требуемой длины ключа `dklen`.

В качестве псевдослучайной функции используется HMAC-SHA256.

Реализация следует конструкции PBKDF2 из RFC 2898.

Формула получения ключа:

```text
DK = T1 || T2 || ... || Tn
```

Каждый блок:

```text
Ti = U1 XOR U2 XOR ... XOR Uc
```

где:

```text
U1 = HMAC(P, S || INT_32_BE(i))
Uj = HMAC(P, Uj-1)
```

Здесь `P` — пароль, `S` — соль, `c` — число итераций, `i` — номер блока.

PBKDF2 выполняет повторные вычисления HMAC, увеличивая стоимость перебора паролей.

При этом количество итераций не заменяет необходимость использования достаточно стойкого пароля.

### 9.2. Команда derive

Для PBKDF2 добавлена подкоманда:

```text
cryptocore derive
```

Общий формат:

```text
cryptocore derive --password-file PASSWORD_FILE [--salt SALT] [--iterations COUNT] [--length LENGTH] --output FILE
```

Поддерживаемые параметры:

| Аргумент | Назначение | Значение по умолчанию |
|---|---|---|
| `--algorithm` | Алгоритм KDF | `pbkdf2` |
| `--password` | Небезопасная передача через argv; только с `--allow-insecure-password-argv` | Не задан |
| `--password-prompt` | Ввод через `getpass` без эха в терминале | Не задан |
| `--allow-insecure-password-argv` | Явное подтверждение риска передачи пароля через argv | Выключен |
| `--show-key` | Явное разрешение печати производного ключа | Выключен |
| `--allow-slow-kdf` | Допускает до 1 000 000 итераций вместо 100 000 | Выключен |
| `--password-env` | Имя переменной окружения с паролем | Не задан |
| `--password-file` | Путь к файлу с паролем | Не задан |
| `--salt` | Соль в HEX | Генерируется случайно |
| `--iterations` | Количество итераций | `100000` |
| `--length` | Длина ключа в байтах | `32` |
| `--output` | Путь к бинарному файлу ключа | Не задан |

Необходимо выбрать один источник: `--password-env`, `--password-file`, `--password-prompt` или небезопасный `--password` с явным флагом `--allow-insecure-password-argv`. По умолчанию ключ записывается только в файл, если задан `--output`.

При отсутствии `--salt` программа генерирует случайные 16 байт.

### 9.3. Формат вывода CLI-3

Результат команды печатается в stdout в формате:

```text
KEY_HEX SALT_HEX
```

**Между `KEY_HEX` и `SALT_HEX` используется ровно один пробел, но эта строка выводится только при явно установленном `--show-key`.**

Это единое соглашение для команды `derive`.

Пример:

```powershell
cryptocore derive --algorithm pbkdf2 --password "password" --allow-insecure-password-argv --show-key --salt 73616c74 --iterations 1 --length 32
```

Ожидаемый результат:

```text
120fb6cffcf8b32c43e7225256c4f837a86548c92ccc35480805987cb70be17b 73616c74
```

Первая часть строки — полученный ключ в HEX.

Вторая часть — соль в HEX.

Программа не выводит исходный пароль.

### 9.4. Salt и повторное получение ключа

Salt — дополнительное значение, которое используется вместе с паролем при получении ключа.

Если соль явно не указана, CryptoCore генерирует случайный 16-байтный salt через CSPRNG.

Пример:

```powershell
cryptocore derive --password-prompt --iterations 100000 --length 32 --output derived.key
```

При двух независимых запусках с автоматически генерируемой солью результаты обычно различаются.

Salt не является секретом, но должен быть сохранён, если необходимо позднее воспроизвести полученный ключ.

Для повторного вычисления того же ключа нужны:

- тот же пароль;
- тот же salt;
- то же число итераций;
- та же длина ключа;
- тот же алгоритм PRF.

В автоматическом тесте проверена генерация 1000 salt длиной 16 байт без повторений.

### 9.5. Сохранение бинарного ключа

Поддерживается параметр `--output`.

Пример:

```powershell
cryptocore derive --password "password" --allow-insecure-password-argv --salt 73616c74 --iterations 2 --length 32 --output sprint7.key
```

В файл записываются **сырые бинарные байты**, а не их шестнадцатеричное представление.

При длине 32 байта размер файла равен 32 байтам.

Проверка в PowerShell:

```powershell
(Get-Item sprint7.key).Length
```

Ожидаемое значение:

```text
32
```

Salt не добавляется автоматически в бинарный файл ключа.

При `--output` по умолчанию печатается только salt (не секрет). Для демонстрации прежнего формата `KEY_HEX SALT_HEX` необходимо отдельно задать `--show-key`; это небезопасно для публичных журналов.

### 9.6. Пароль из переменной окружения

Передача пароля через `--password` удобна для демонстрации, однако пароль может сохраниться в истории команд.

Поэтому дополнительно реализован способ `--password-env`.

Пример для PowerShell:

```powershell
$env:CRYPTOCORE_PASSWORD = "TestPassword123!"
```

Выполнение:

```powershell
cryptocore derive --password-env CRYPTOCORE_PASSWORD --salt 00112233445566778899aabbccddeeff --iterations 100000 --length 32 --output derived.key
```

Удаление переменной:

```powershell
Remove-Item Env:\CRYPTOCORE_PASSWORD
```

Использование переменной окружения уменьшает необходимость передавать пароль непосредственно как аргумент команды `cryptocore`, но не обеспечивает абсолютной защиты секрета.

### 9.7. Пароль из файла

Также поддерживается передача пароля через:

```text
--password-file FILE
```

Например:

```powershell
cryptocore derive --password-file password.bin --salt 00112233445566778899aabbccddeeff --iterations 100000 --length 32 --output derived.key
```

В режиме `--password-file` пароль читается как последовательность бинарных байтов.

Если файл содержит завершающий перевод строки, он тоже учитывается как часть пароля.

Файл с паролем должен храниться с ограниченными правами доступа и не добавляться в Git.

### 9.8. Ограничение длины ключа

Для предотвращения чрезмерного выделения памяти через `--length` добавлено ограничение длины производного ключа.

Допустимый диапазон:

```text
1 <= dklen <= 65536
```

Максимальная длина результата — **65 536 байт (64 КиБ)**.

Ограничение применяется как на уровне CLI, так и непосредственно в реализации PBKDF2.

Пример неверного вызова:

```powershell
cryptocore derive --password-file password.bin --salt 73616c74 --iterations 1 --length 65537 --output derived.key
```

Ожидается ошибка:

```text
cryptocore: error: --length must not exceed 65536 bytes
```

Проверка выполняется до вычисления PBKDF2.

Это ограничение предотвращает запрос чрезмерно длинного результата, однако не устраняет все риски отказа в обслуживании: очень большое количество итераций также может создавать значительную вычислительную нагрузку.

### 9.9. Очистка пароля и ключа из памяти — IO-4

В `run_derive()` предусмотрена дополнительная обработка секретных данных.

Пароль после чтения переводится в изменяемый буфер `bytearray`.

Полученный ключ также помещается в изменяемый буфер.

После завершения операции в блоке `finally` выполняются:

1. Перезапись содержимого изменяемого буфера пароля нулевыми байтами.
2. Перезапись содержимого изменяемого буфера ключа нулевыми байтами.
3. Удаление локальных ссылок на буферы через `del`.

Блок `finally` выполняется как после успешного завершения, так и при ошибках вычисления или записи результата.

Принцип очистки:

```python
try:
    ...
finally:
    if password is not None:
        password[:] = b"\x00" * len(password)

    if key is not None:
        key[:] = b"\x00" * len(key)

    del password
    del key
```

В `resolve_password()` предусмотрено отсутствие вывода пароля в stdout и stderr.

Пароль не включается в штатные информационные сообщения или сообщения об ошибках программы.

**Ограничение:** Python не предоставляет универсальной гарантии полного удаления всех копий секретов из памяти. Объекты `str` и `bytes` неизменяемы, а промежуточные данные HMAC, временные буферы, аргументы командной строки и другие копии могут продолжать существовать независимо от очищаемых `bytearray`.

Поэтому применённый подход является мерой снижения риска (*best-effort zeroization*), а не гарантированной очисткой всей оперативной памяти.

### 9.10. Тестовые векторы PBKDF2 — TEST-1

### 9.12. Иерархия ключей

Дополнительно реализована функция:

```python
derive_key(master_key, context, length)
```

Модуль:

```text
src/kdf/hkdf.py
```

Функция позволяет получать несколько независимых по назначению производных ключей из одного master key.

Используется детерминированная HMAC-конструкция:

```text
HMAC(master_key, context || counter)
```

Для получения ключа нужной длины вычисляются последовательные блоки HMAC, затем результат обрезается до запрошенного количества байтов.

Параметр `context` служит идентификатором назначения ключа.

Пример:

```python
from kdf import derive_key

master_key = b"0" * 32

encryption_key = derive_key(
    master_key,
    "encryption",
    16,
)

authentication_key = derive_key(
    master_key,
    "authentication",
    32,
)

print("Encryption:", encryption_key.hex())
print("Authentication:", authentication_key.hex())
print("Different:", encryption_key != authentication_key)
```

Разные контексты порождают разные ключи из одного master key.

При одинаковых входных данных результат остаётся детерминированным.

Важно: модуль называется `hkdf.py` в соответствии со структурой технического задания, но реализует упрощённую HMAC-конструкцию для иерархии ключей. Она **не является полной реализацией HKDF** из RFC 5869.

### 9.14. Рекомендации по безопасности PBKDF2

Для безопасного получения ключей необходимо учитывать следующие положения:

- Использовать достаточно длинный и непредсказуемый пароль.
- Генерировать отдельный случайный salt для каждого независимого получения ключа.
- Использовать salt длиной не менее 16 байт.
- Хранить salt и параметры KDF, необходимые для восстановления производного ключа.
- Подбирать число итераций в соответствии с требованиями безопасности и вычислительными ресурсами.
- Не публиковать производные ключи и пароли.
- Избегать передачи реальных паролей в открытом виде через аргументы командной строки.
- Учитывать ограничения очистки секретов из памяти в Python.

Значение `100000` итераций по умолчанию установлено техническим заданием Sprint 7 и не является универсальной актуальной рекомендацией для всех производственных систем.

Для новых приложений, предназначенных для хранения паролей, целесообразно рассматривать специализированные функции, устойчивые к массовому перебору, например Argon2id.

В последнем локальном измерении AES-128 CTR для 1 МиБ получены **1,96 МиБ/с при шифровании** и **2,19 МиБ/с при расшифровании** (успешный round-trip). Реальные результаты PBKDF2 для 10 000, 100 000 и 1 000 000 итераций приведены в разделе 9.13.

Дополнительно существует сценарий потоковой обработки большого файла:

```powershell
python scripts\verify_large_stream.py --gib 1.05 --yes
```

**Тест с файлом более 1 ГиБ пока не подтверждён выполненным запуском**. Команда может требовать несколько гигабайт свободного места. Не следует заявлять этот эксперимент выполненным до получения его результата.

## 13. Ограничения проекта

CryptoCore является учебной реализацией и имеет ряд ограничений.

Собственные реализации SHA-256, SHA3-256, HMAC и PBKDF2 существенно уступают оптимизированным криптографическим библиотекам по производительности.

Обычные AES-режимы ECB, CBC, CFB, OFB и CTR не обеспечивают встроенную проверку подлинности.

В GCM необходимо соблюдать уникальность nonce для каждого ключа. В файловом CLI и высокоуровневых API GCM/EtM (а также `cli.encrypt_data` для режимов с IV) используется локальный SQLite-реестр использованных сочетаний AES-ключа и nonce/IV. Его нельзя сбрасывать между операциями с тем же ключом; реестр не синхронизируется между компьютерами.

Начиная с 0.8.1, файловый CLI обрабатывает основной файл и AAD порциями; отдельные библиотечные функции, принимающие `bytes`, по-прежнему требуют вход целиком.

Очистка секретов через `bytearray` ограничивается изменяемыми буферами и не может гарантировать удаление всех копий данных из памяти интерпретатора Python.

Для PBKDF2 введены пределы: ключ до 65 536 байт, число итераций до 100 000 по умолчанию и до 1 000 000 только с `--allow-slow-kdf`; даже 100 000 итераций на чистом Python могут выполняться долго.

При использовании `derive` ключ выводится в stdout **только** при `--show-key`. Без этого флага требуется `--output` и выводится только salt.

CryptoCore не следует применять как основную криптографическую библиотеку в производственных системах без дополнительного анализа, тестирования и аудита безопасности.

## 16. Дополнение к Sprint 8: исправления безопасности v0.8.1

Подробная карта восьми замечаний преподавателя и оставшихся ограничений: [docs/SECURITY_REVIEW_2026.md](docs/SECURITY_REVIEW_2026.md).

- **Повтор nonce/IV:** SQLite-реестр `~/.cryptocore/nonces.sqlite3` атомарно запрещает повторное использование пары ключ+nonce при CLI-шифровании. Для тестов и отдельных установок путь настраивается переменной `CRYPTOCORE_NONCE_DB`. При недоступном реестре шифрование прекращается. Удаление или откат базы, несколько машин с одним ключом не защищаются этой локальной проверкой; следует избегать распределённого повторного использования одного ключа.
- **AES-ключи:** автоматически сгенерированный ключ записывается в `<output>.key` как 16 бинарных байтов и не печатается без `--show-key`. Для дальнейшего использования: `--key-file FILE`. На Unix файл создаётся с правами `0600`; на Windows защита дополнительно зависит от ACL каталога.
- **PBKDF2:** `--password` требует `--allow-insecure-password-argv`, для безопасного интерактивного ввода существует `--password-prompt`; ключ не печатается без `--show-key` и должен сохраняться через `--output`. Для более чем 100 000 итераций до 1 000 000 требуется `--allow-slow-kdf`.
- **Потоковый CLI:** AES-ECB/CBC/CFB/OFB/CTR, GCM и EtM обрабатывают файлы фрагментами до 64 КиБ с атомарной заменой конечного файла. Для GCM используется нативный AES-GCM из PyCryptodome, с проверкой тега до публикации открытого текста. Начиная с 0.8.2, `modes.GCM` также использует нативный backend; исторический Python-GHASH сохранён только в учебном примере вне `src`.
- **AAD:** `--aad-file` поддерживается для GCM и EtM, проверка идёт по файлу частями.
- **Zeroize:** очищаются управляемые изменяемые буферы; полной гарантии удаления `str`, `bytes` и копий на уровне интерпретатора Python нет.

Пример без секретов в аргументах и stdout:

```powershell
cryptocore --algorithm aes --mode gcm --encrypt --input plain.bin --output encrypted.gcm
cryptocore --algorithm aes --mode gcm --decrypt --key-file encrypted.gcm.key --input encrypted.gcm --output restored.bin
cryptocore derive --password-prompt --iterations 100000 --output derived.key
```

Обычные `--key HEX` и `--show-key` предусмотрены для совместимости и образовательных демонстраций: их не рекомендуется применять с реальными секретами.

## 17. Дополнительные исправления безопасности — CryptoCore 0.8.2

Версия 0.8.2 предназначена для повторной сдачи замечаний преподавателя **поверх уже опубликованного коммита 0.8.1**. Форматы шифртекста и CLI сохранены.

**Что изменено после 0.8.1:**

- `modes.GCM` теперь использует `PyCryptodome AES.MODE_GCM` вместо табличного Python GHASH. Старый GHASH вынесен в `docs/examples/ghash_reference.py` **только для образовательной демонстрации** и не выполняется при шифровании. Использование внешнего backend не доказывает безусловную constant-time защиту на любом оборудовании.
- Проверка повторного nonce/IV действует и в **высокоуровневом библиотечном API**: `modes.GCM.encrypt`, `aead.EncryptThenMAC.encrypt`, `cryptocore.cli.encrypt_data` (CBC/CFB/OFB/CTR), а не только в файловом CLI. Библиотечный EtM и файловый EtM одинаково индексируют IV по производному ключу AES.
- Команда `derive --output` теперь эксклюзивно создаёт новый файл для ключа и не перезаписывает существующий файл. На Unix устанавливаются разрешения `0600`; Windows опирается на ACL каталога.
- В `tests/conftest.py` организован отдельный SQLite-реестр для каждого теста; новые регрессионные проверки находятся в `tests/integration/test_security_followup_v082.py`.
- Обновлены `SECURITY.md`, `docs/SECURITY_REVIEW_2026.md`, `docs/SECURITY_AUDIT.md`, `docs/QA_CHECKLIST.md`, `docs/API.md` и руководство разработчика.

**Неизменяемые ограничения:** локальный реестр нельзя считать глобальным при использовании одного ключа на нескольких компьютерах; низкоуровневые учебные функции AES допускают IV без реестра; полная очистка памяти CPython не гарантируется; встроенная защита аутентификации отсутствует у ECB/CBC/CFB/OFB/CTR. Используйте GCM/EtM, `--key-file` и `--password-prompt`.
