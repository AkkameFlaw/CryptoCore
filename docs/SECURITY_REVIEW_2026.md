**Дата:** 18 ноября 2026 г.

**Статус:** предложенные исправления с регрессионными тестами; не независимый аудит и не сертификация безопасности.

## Дополнительные защитные механизмы

- При расшифровании **GCM** выполняется первый проход аутентификации до записи plaintext; при втором проходе тег проверяется повторно до атомарного опубликования результата.
- При расшифровании **EtM** HMAC проверяется до дешифрования и повторяется на втором проходе для защиты от изменения файла между чтениями.
- Реестр использует уникальный индекс SQLite и не хранит исходные ключи. Его место по умолчанию — `~/.cryptocore/nonces.sqlite3`. Для изолированных тестов: `CRYPTOCORE_NONCE_DB=...`.
- На Unix автоматически создаваемые файлы AES-ключей имеют права `0600`, временные выходные файлы создаются с приватными правами. На Windows итоговый контроль зависит от ACL и настроек каталога.
- Новый режим `--key-file` принимает **ровно 16 сырых байтов**, не HEX-текст; пример сохранённого файла: `<output>.key`.
- Файлы PBKDF2-паролей имеют дополнительный лимит 4096 байт, чтобы избежать случайной загрузки очень большого файла.
- Для GCM-класса `modes.GCM` и базовых AES/CTR функций прямой библиотечный вызов не использует persistent registry: это отдельная обязанность вызывающего кода.

## Совместимость и отличия

Изменены настройки CLI. Старые демонстрационные вызовы `derive --password "..."` теперь требуют явного `--allow-insecure-password-argv`. Для вывода `KEY_HEX SALT_HEX` нужен также `--show-key`. Без этих флагов предпочтителен `--password-prompt --output FILE`.

Форматы шифртекста оставлены без изменений: ECB — ciphertext; CBC/CFB/OFB/CTR — `IV(16)||ciphertext`; GCM — `nonce(12)||ciphertext||tag(16)`; EtM — `nonce(16)||ciphertext||HMAC(32)`. На CLI нативный GCM должен быть совместим с исходным учебным GCM (это проверяется интеграционными тестами).

**Точность формулировки про EtM:** повтор nonce в AES-CTR приводит к повтору потока шифрования и серьёзному нарушению конфиденциальности. При корректном ключевом разделении и HMAC-SHA256 это само по себе не равнозначно компрометации аутентификации, в отличие от тяжёлых последствий повторного nonce для GCM. Повтор nonce запрещён для обоих.

## Проверки

```powershell
python -m pip install --no-build-isolation --no-deps -e .
pytest tests\integration\test_security_hardening.py -v
pytest tests\test_aead_cli.py tests\test_derive_cli.py tests\test_cli.py -v
python tests\run_tests.py --enforce-coverage
```

Для запуска тестов в полностью изолированной среде можно задать отдельный путь реестра `CRYPTOCORE_NONCE_DB`; он не должен совпадать с вашим рабочим реестром.

Исправленные тесты, зависящие от старого печатаемого ключа или безусловного argv-пароля, обновлены. Результаты проверок в среде разработки: 57 тестов связанных CLI-модулей прошли с временным совместимым AES backend на базе `cryptography` для тестирования; требуется полная проверка **оригинальным PyCryptodome** в Windows-окружении пользователя. Прежние 328 тестов и покрытие 91.63% относятся к версии 0.8.0, а не доказательству для нового 0.8.1.

## Дальнейший аудит

Для полноценной защиты секретов необходимо использовать специализированную криптографическую библиотеку с проверенными реализациями, управление ключами/nonce на уровне сервиса, защиту файловых разрешений и независимый аудит. Учебные реализации Python-GHASH, HMAC, SHA и PBKDF2 оставлены для образовательной работы и не заменяют промышленную криптографию.

### Дополнительная ручная проверка файлов свыше 1 ГиБ

В `scripts/verify_large_stream.py` предусмотрен опциональный сценарий с разреженным файлом, потоковым AES-GCM, расшифрованием и SHA-256 сравнением без чтения файла целиком в память. Он требует не менее 3 ГиБ свободного дискового пространства на 1 ГиБ входных данных и запускается **только вручную**:

```powershell
python scripts\verify_large_stream.py --gib 1.05 --yes
```

Этот сценарий **ещё не был выполнен** в пользовательской Windows-среде и не включён в обычные 328 тестов. `tracemalloc` измеряет только аллокации Python, а не все буферы и расходы операционной системы.
