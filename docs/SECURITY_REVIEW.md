# CryptoCore 0.8.2 — повторная проверка восьми замечаний преподавателя

**Исходная база:** CryptoCore 0.8.1 после коммита Sprint 8. **Тип оценки:** повторная техническая проверка исправлений; не независимый аудит и не гарантия безопасности. Изменения 0.8.2 готовятся как новый коммит поверх 0.8.1.

| № | Замечание | Что изменено | Оставшееся ограничение |
|---|---|---|---|
| 1 | Повторное использование nonce/IV | Помимо файлового CLI регистрируется каждая операция в `modes.GCM.encrypt`, `aead.EncryptThenMAC.encrypt`, `cli.encrypt_data` для CBC/CFB/OFB/CTR. Для EtM регистрируется производный AES-ключ, согласованно с файловым CLI. Проверяется повтор между API и CLI и конкурентные записи. | Реестр SQLite локален, не синхронизируется между машинами; низкоуровневые учебные функции AES принимают IV без реестра. Нельзя удалить/откатить БД, повторно используя ключи. |
| 2 | Пароль `--password` в argv | Ещё в 0.8.1: небезопасный флаг требует `--allow-insecure-password-argv`; доступны `--password-prompt`, `--password-file`, `--password-env`. | Явное разрешение не скрывает пароль из истории и списка процессов. `getpass` временно создаёт `str` в памяти. |
| 3 | Ключ в stdout | Ещё в 0.8.1: печать только с `--show-key`; обычный AES-ключ записывается в `.key`. В 0.8.2 бинарный результат `derive --output` также создаётся эксклюзивно с приватными правами на Unix. | Вывод по явному флагу небезопасен; файлы ключей и ACL каталогов нужно охранять, `--key HEX` тоже небезопасен в argv. |
| 4 | Табличный Python-GHASH | **В 0.8.2 полностью убран из рабочего API GCM**: `modes.GCM` теперь использует `PyCryptodome AES.MODE_GCM`, как и файловый CLI. Старый пример находится лишь в `docs/examples/ghash_reference.py`. | Нет формально подтверждённого constant-time для каждого процессора и всех остальных компонентов Python; программный AES на некотором оборудовании может использовать таблицы. |
| 5 | Zeroization best-effort | Разрешён скрытый ввод, ограничена печать ключей, контролируемые `bytearray` затираются после работы. Дополнительно безопаснее записывается полученный ключ. | **Гарантировать очистку всех `str`/`bytes`, временных буферов и Python heap нельзя**. Это фундаментальное ограничение среды, а не устранённая уязвимость. |
| 6 | Файл целиком в RAM | Ещё в 0.8.1: файловый CLI использует потоковые блоки по 64 КиБ и атомарную публикацию; GCM/EtM проверяют аутентификацию. | Библиотечные методы, принимающие `bytes`, остаются in-memory по контракту; тест >1 ГиБ на Windows требуется выполнить отдельно. |
| 7 | Нет верхнего лимита PBKDF2 | Ещё в 0.8.1: 100000 итераций по умолчанию, до 1000000 с `--allow-slow-kdf`, в библиотеке абсолютный предел 1000000. | Длительная синхронная операция может быть DoS даже при лимите: не предоставлять публичный удалённый `derive` без бюджетов. |
| 8 | `--aad-file` только GCM | Ещё в 0.8.1: файл AAD потоково обрабатывается в GCM и EtM, отрицательные тесты подтверждают обнаружение изменения AAD. | `EncryptThenMAC.encrypt(bytes, aad=bytes)` — API в памяти; файлы с AAD используйте через `streaming`/CLI. |

## Границы заявленной защиты

- Реестр предотвращает повтор **при условии общей неоткатываемой БД для операций с тем же ключом**. Он не делает невозможным повтор в многомашинном сервисе без общего состояния. Для безопасного продакшн-развёртывания следует использовать отдельные ключи на каждого отправителя либо централизованное управление nonce.
- Реестр не является механизмом проверки целостности шифртекста. Для этого выбирайте GCM/EtM. Классические режимы CBC/CTR/CFB/OFB остаются без аутентификации.
- `--password-prompt` минимизирует раскрытие пароля, но не гарантирует его удаление из памяти. Высокоуровневые API с `bytes` не предназначены для 1+ ГиБ без потокового интерфейса.
- Подмена старого Python GHASH нативным backend не означает сертификацию и не исключает боковые каналы во всех программных компонентах. Проблемы измерения времени требуют независимого исследования.

## Изменения тестирования

Добавлено `tests/conftest.py`, изолирующее базу nonce для каждого случая тестирования, чтобы детерминированные NIST-векторы не засоряли пользовательскую базу. Отдельные тесты в `tests/integration/test_security_followup_v082.py` проверяют повтор в новых API, между файловым CLI и библиотечным API, невозможность шифрования при отказе реестра, атомарность параллельной регистрации и аутентификацию GCM.

```powershell
python -m pip install --no-build-isolation --no-deps -e .
pytest tests\integration\test_security_followup_v082.py -v
python tests\run_tests.py --enforce-coverage
python scripts\audit_public_api.py
```

**Результат пользовательской проверки 0.8.1:** `409 passed`, `94.69%` общего покрытия строк и ветвей. **Не считать эти показатели результатом запуска версии 0.8.2**, пока новые команды не выполнены на Windows с установленным PyCryptodome.

### Проверка больших файлов (отдельно)

```powershell
python scripts\verify_large_stream.py --gib 1.05 --yes
```

Требуются свободное место на диске и время; большой эксперимент не входит в обычный набор unit/integration. Результат не следует утверждать до фактического запуска.

**Основа рекомендаций:** NIST SP 800-38D (уникальность GCM IV), документация и changelog PyCryptodome по реализации AES/GHASH.


**Предварительный прогон 0.8.2 (Linux, Python 3.13, тестовый совместимый адаптер AES на основе `cryptography`):** 422 теста успешно пройдены, 95,40% общего покрытия строк и ветвей. Это не заменяет полный запуск с настоящим PyCryptodome на Windows; адаптер не входит в поставку.
